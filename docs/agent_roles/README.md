版：1.1 / 作成日：2026-10-25 / 運用更新：2026-10-30。制作者用。publicへ置かない。

## 適用する作業モード

最初に [AGENTS.md](../../AGENTS.md) のモード選択に従う。詳細は [WORK_MODES.md](../WORK_MODES.md)。軽量修正はメインのみで、この専門担当フローや詳細な委任記録を適用しない。通常制作も原則メインのみで、関連資料と関連テストに絞り、必要な場合だけ本書の受け渡し手順を使う。第3節の設計→別担当レビュー→作者承認→委任実装の一連のフローは重要設計に適用する。

2026-10-30の作者指定により、過去の一律の事前・事後評価はモード別運用へ変更する。重要設計の作成前後の評価・最大5回の改善は維持し、軽量修正へ拡張しない。個別依頼で指定された評価・承認条件は優先する。本書の2026-10-25の「今回」は当時の作成記録であり、全モードの義務を意味しない。

## 1. 今回の変更と入口

現在の実行環境ではカスタム名を指定して起動できず、通常のサブエージェントは起動可能、というユーザーからの運用条件を前提とする。

既存TOMLは削除・変更せず、専門指示をMarkdownへ整理し、通常サブエージェントの起動メッセージに明示的に渡す。これはランタイム設定の変更や、カスタムエージェント認識の修復ではない。task_nameを役名にしても、TOMLが適用されたとは扱わない。

公式の[Subagents説明](https://learn.chatgpt.com/docs/agent-configuration/subagents)は、親による作業分割と結果統合、明確な依頼、書き込み競合への注意を説明している。本書の全文引き渡し・受領確認・版管理は、このプロジェクトで採用する運用規約であり、Codexに自動実装された機能ではない。

## 2. 既存資料との関係

AGENTS.md、既存docs、planning、.codex/README.md、4つのTOMLは変更していない。前回の「名前でカスタム役を起動する」説明に対して、本書が通常サブエージェント方式の追加手順となる。既存の物語設定や上位指示を上書きしない。

専門指示本文はTOMLのdeveloper_instructionsを保持し、その外側に受領・報告の手順だけを追加した。各役の冒頭に元TOMLのハッシュを記録。将来TOMLまたはMarkdownが変わった場合は差を確認し、両者が自動同期するとは考えない。

モデル・推論強度は起動時に固定しない。現在のツールが継承する設定を使い、他のモデルへ勝手に置き換えない。TOMLのfeatures/skills、サンドボックス、ツール権限等は、Markdownの受け渡しだけでは適用されない。読み取り専用という指示もOSの隔離とは別であり、メインが実施内容と差分を確認する。

## 3. 重要設計の制作フロー

### 1）メインが現在地を確認

AGENTS.md、docs/README.md、docs/08-open-questions.mdを読み、対象に関係する01〜09の資料と現行実装を照合する。デザイン対象のplanningがあれば全文読む。

既存の資料は2026-10-23の調査記録であり、その日付以降も同じと決めつけない。今回は世界観や制作進捗の再確定をしていない。

メインは依頼範囲、作者承認の有無、現在の未コミット変更、対象ページ、変更禁止事項、成果物、停止条件をまとめる。ユーザーから今回の委任が許可されているか確認し、本書の存在だけを根拠に自動委任しない。

### 2）設計担当へ全文を渡す

通常のサブエージェントを一つ起動し、story_designer.md全文と案件指示を明示的に渡す。ファイルを読むよう伝えるだけにしない。

設計段階はファイル編集なし。案のID・版を決め、対象ページごとの疑問、根拠、操作、得られる情報、次の導線、伏線回収、未確定事項を提案させる。未実装ページの全補完や、ページ番号の予約をさせない。

### 3）別担当で整合性を確認

設計結果を受け取ってから、別の通常サブエージェントへcontinuity_reviewer.md全文を渡す。レビュー対象の案をID・版とともに全文または欠落のない確定スナップショットで渡す。

作者資料と現行ページを照合し、確定/原案/推測/未確定、意図したミスリード/単純矛盾、既知/新規の問題を分ける。読み取りのみで修正させない。

順序依存があるため、このレビューを案の完成前に「その案を検証した」とはしない。独立した現況調査だけを並行させる場合も、提案レビューとは別に記録する。

### 4）メインが統合し作者へ提示

設計・レビュー両方を待ち、根拠と現行実装をメインでも確認する。必要な修正提案は設計担当へ返し、変わった案を再レビューする。

作者に提示するものは、案の版、追加/変更候補、体験上の狙い、開示情報、導線、未確定・要承認事項、予定編集ファイル、テスト、資料更新の範囲。

ここで停止して作者の承認を待つ。レビュー合格、担当の提案、作者の無回答、単なる「いいね」等を仕様全体への承認と推定しない。承認の対象や範囲が曖昧なら確認する。

### 5）承認後だけ実装

作者が承認した具体的な案の版と範囲を記録してから、web_developer.md全文と実装契約を渡す。案が変更された場合、以前の版への承認を流用しない。

許可編集ファイルを具体的に列挙し、共有CSS・検索DB・アーカイブ辞書・改番の担当を一人に決める。権限が足りない、設定が未確定、範囲拡大が必要な場合はメインへ戻す。

安全な既定は実装担当一人＋共有ファイル統合担当としてのメイン。個別HTMLの実装と共有ファイル更新を分ける場合は、その接続待ちも記録する。実装担当を複数使うときはファイル集合を完全に分ける。

実装担当は起動直後に受領確認し、メインからの着手許可が来るまではファイル編集を開始しない。手順はDISPATCH_TEMPLATESを参照。

### 6）実装後にテスト・再確認

実装担当が構文、リンク、画像、検索の正解/不正解、EX非登録、番号重複、旧アーカイブ保存の再訪、必要な画面幅を検証する。メインは差分と報告の整合を確認する。

関連する場合は既存のnode scripts/check-community-archive.cjsを使うが、全ページの保証とはみなさない。更新スクリプトをテスト代わりに実行しない。

重要設計ではレビュー担当へ、同じ役割全文と実装後の対象版・差分を渡して再照合と評価を依頼する。評価が不十分なら改善点を求め、承認範囲内で修正・再評価する（十分な評価または最大5回まで）。テストに失敗した場合は完了にせず、承認済み範囲で修復するか、仕様変更が必要なら作者へ戻す。未検証事項は明記する。

この段階の動作テストは開発者としての確認であり、arg_playerの初見テストではない。

### 7）資料と進捗を更新

テスト結果を確認後、メインが設計資料・ページ一覧・導線・検索一覧・課題・制作進捗の更新を担当する。担当エージェントに同じ資料を同時編集させない。

資料への追記/変更も、作者が許可した具体的なファイルと範囲で行う。今回の「新規資料以外は変更しない」という制約がある作業では、既存資料を更新せず、新しい実施記録へ更新候補と保留を残す。AGENTS.mdやTOMLを当然に更新対象へ含めない。

提案段階を「実装済み」にせず、未実装・未検証・未承認を残す。承認対象、変更ファイル、検証、残課題を作者へ報告する。資料更新が保留なら制作・資料のどこまでが完了したかを分ける。

## 4. 指示を渡したこと・実施したことの確認

メインは起動前に役割Markdownの全文を読み、途中で切れていないことを確認する。省略表示されたツール出力しか読めていない場合は続きを取得する。全文を起動メッセージに含められない場合は、そのまま起動せず依頼を分割する。

起動時に渡すもの：

- 役割Markdown全文（要約やパスだけで代替しない）
- 役割版とSHA-256（ファイルの実バイト列を基準）
- 案件ID・ジョブID・対象案の版・具体的な依頼
- 作者承認の根拠と範囲、または「未承認・提案のみ」
- 読み取り対象と編集許可対象、禁止対象
- 出力形式、停止条件、実装時は編集着手の可否

使える起動ツールのmessage等の指示欄へ本文を入れる。task_nameは整理用ラベルとして扱う。モデル等は省略し、特定のカスタム役を選ぶ引数を想像して足さない。

現在のcollaboration.spawn_agentを使う場合も、役割本文はmessageへ明示的に含める。作者側担当では必要な案件情報をすべて明示したうえでfork_turnsをnoneにする運用が可能だが、これはコンテキスト整理であり、初見性・権限隔離の保証ではない。現在のツール仕様が変われば読み替え、存在しない引数で起動しない。

起動ツールが返す実際のagent IDを記録する。受領確認を読み、役割・対象・編集境界が合っているか確認する。実装では、メインが確認してから同じID宛てに着手許可を送る。

完了時は自己申告だけでなく、根拠、結果の案の版、差分、実際の検証結果をメインが照合する。ハッシュを復唱しただけで完全遵守を保証したと扱わない。

## 5. 記録と競合防止

[記録テンプレート](RUN_RECORD_TEMPLATE.md)を用い、メインが作業会話または作者に許可された新規の実施記録へ残す。ファイル保存するなら例としてdocs/agent_runs/<案件ID>.mdが使えるが、今回はそのフォルダや実施記録は作っていない。

記録には、役割のパス・版・SHA、実際に渡した全文と依頼、agent ID、受領確認、対象案の版、結果、作者承認、許可ファイル、所有者、テスト、メインの確認を残す。役割内容の転送に失敗した場合や未起動も、そのまま記録する。

- 同じファイルに書く担当は同時に一人。メイン自身も例外ではない。
- 既存のユーザー変更を担当変更と混同しないよう、作業前の状態を保存/把握する。
- 共有ファイルが必要になったら、先行担当を待つか、停止・引き継ぎを確認してから担当を交代する。
- 読み取りレビューは、対象版を固定するか実装完了を待って行う。途中の状態を最終版のレビューとしない。
- 書き込み競合や許可外変更を検知したら追加編集を止め、メインへ報告。無断で他担当の差分を巻き戻さない。
- 担当間の承認と作者承認は別。新たな設定・ファイル範囲をメッセージだけで拡大しない。

## 6. arg_playerは開発フローから分離

arg_player.mdは整理のみ。通常の開発用サブエージェントとして起動せず、履歴を継承しない独立環境を別途構築する。役割を与えた通常の開発担当へ「初見のつもりで」と依頼して代用しない。

中立な作業場所、作者AGENTS.mdの非読込、新しいブラウザ状態、ブラウザ通常操作のみ、作者資料や解答にアクセスできない環境が必要。渡す物語情報はスタートURLだけ。親側から想定ルートや設計レビューを渡さない。

TOMLの機能制限はMarkdownへ移しただけでは機械的に適用されない。独立環境側でアクセスを制限し、汚染があれば停止する。今回は構築・起動・プレイをしていない。

角括弧の欄は実際の値へ置き換える。空欄・仮の承認のまま実装しない。

## 8. 今回の確認範囲

4つの役割Markdown、共通フロー、受け渡しテンプレート、記録テンプレートの新規作成のみ。元TOMLとの本文一致・相対リンク・既存ファイル保全を検証する。

2026-10-25の確認結果：4役の専門指示本文は元TOMLのdeveloper_instructionsと一致し、記載した元ファイルのSHA-256も一致。新規資料の相対Markdownリンクに未作成先なし。開始時の既存147ファイルはすべて内容ハッシュが一致し、変更・削除なし。追加はこのフォルダの7 Markdownファイルのみ。

通常サブエージェントの実起動、専門指示に従った実作業、初見環境の動作は今回試していない。手順が自動実行される機能を追加したわけではなく、メインがこの運用資料を読み、明示的な依頼ごとに実行する方式である。
