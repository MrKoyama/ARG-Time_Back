# 通常サブエージェントへの指示テンプレート

[共通フロー](README.md)に従い、メインCodexが利用する。これはサブエージェントに「このファイルを読むだけ」で済ませるためのものではない。

2026-10-30更新：[作業モード](../WORK_MODES.md)で実際に委任すると判断した場合だけ使用する。軽量修正は委任禁止、通常制作は原則メインのみ。以下の欄・チェック・詳細記録を委任しない作業へ適用しない。通常制作で役割を一つ委任しても、不要な別役を自動起動しない。重要設計では従来の設計・別担当レビュー・作者承認を維持する。

役割のパス・task_nameだけを渡すことは禁止。メインは以下の雛形を実データで埋め、指定の役割Markdown全文を実際に起動メッセージへ展開する。未展開のプレースホルダーを送らない。役割はツールの特別なagent_typeではなく、通常サブエージェントへの明示的な作業指示である。

## A. 全役共通の送信枠（作者側3担当専用）

```text
【案件】
案件ID：<一意の案件ID>
作業モード・委任理由：<通常制作で委任が必要な理由 / 重要設計>
ジョブID：<一意のジョブID>
担当役割：<story_designer / continuity_reviewer / web_developer>
役割ファイル：<プロジェクト基準パス>
役割版：<ファイル冒頭の版>
役割全文SHA-256：<実バイト列のハッシュ>
プロジェクト絶対パス：<実際のARG-Time_Backのパス>
起動方式：通常サブエージェント。task_nameは整理用ラベルであり、TOMLの適用は前提にしない。

【明示的な役割指示・全文開始】
<メインが役割Markdown全文をここへ展開する。パスや要約だけで代替しない>
【明示的な役割指示・全文終了】

【今回の作業】
目的：<この担当で得たい成果>
対象案・対象実装のIDと版：<固定した版。未作成ならその旨>
作者承認：<作者の実際の発言の参照・承認範囲 / 未承認・提案のみ>
参照資料：<実在する文書・公開ページと必要な案件情報>
確定事項：<承認済み事項>
未確定・変更禁止：<解法・人物・時系列・番号などの境界>
許可編集ファイル：<具体的なパス一覧 / なし>
共有ファイル所有者：<メインまたは担当ID / 編集なし>
成果物：<提案・レビュー・承認仕様の実装等>
検証：<確認項目>
停止条件：<作者判断・範囲拡大・競合等>
着手状態：<読み取り調査のみ開始可 / 受領確認のみ・編集着手待ち>

【受領確認】
最初にジョブID、役割名・版・渡されたSHA、目的、許可編集ファイル、禁止事項を返してください。
全文が欠けている・対象版や承認根拠が足りない場合は、その不足を報告してください。
編集着手待ちの場合は確認だけで止まり、メインの明示許可まで編集しないでください。

【完了報告】
実施内容と対象版、根拠パスと行/見出し、状態区分、変更ファイル、テスト結果、
未検証、未確定・作者確認事項、後続担当への注意を返してください。
許可のないファイル保存・別エージェント作成はしないでください。
```

起動ツールの戻り値でagent IDを受け取り、[記録](RUN_RECORD_TEMPLATE.md)へ残す。役割名だけで「正しい担当が起動した」と記録しない。

モデル・推論強度の指定は原則省略する。カスタム名の起動ができないからといって別モデルや別プロバイダへ勝手に切り替えない。使えるツールの実際の引数を確認し、架空のパラメータやコマンドを追加しない。

## B. story_designerの案件欄の例

```text
目的：現在地を確認し、次の制作単位の候補を提示する。
対象案：<案件ID>-PLAN-v1を提案する。
作者承認：未承認・提案のみ。新しい重要設定の決定権はない。
許可編集ファイル：なし。
成果物：
- 根拠のある現在地
- ページごとの入口、疑問、提示する事実、推理/操作、小さな答え、次の導線
- 伏線の配置と回収、開示しない情報
- 未確定事項と作者に必要な判断
- 想定する実装・検証・資料更新の範囲（編集はしない）
着手状態：読み取り調査のみ開始可。
```

上記は案件欄の例であり、Aの役割全文展開を省略してよいという意味ではない。

## C. continuity_reviewerの案件欄の例

```text
目的：設計担当が提出した案を、現行設定・ページと照合する。
対象案：<案件ID>-PLAN-v1。以下に対象案全文を添付。
<設計担当の案の全文、根拠、未確定事項をここへ展開>
作者承認：未承認。レビュー合格は作者承認ではない。
許可編集ファイル：なし。
成果物：
- 対象案の版と確認範囲
- 指摘ID、重要度、根拠、影響、確定/推測/未確定
- 意図したミスリードと矛盾の区別
- 既知課題との対応、追加の作者判断
- 問題なしの箇所と未確認範囲
着手状態：読み取り調査のみ開始可。
```

設計担当とは別の通常サブエージェントへ渡す。案を受け取る前の調査を、その案のレビュー済み証拠にしない。対象案が更新されたら版を進め、変更点を再レビューする。

## D. web_developerの案件欄の例

```text
目的：作者が承認した案の指定範囲だけを実装する。
対象案：<承認済み案IDと版>
作者承認：
- 作者発言：<実際の発言の参照と必要な引用>
- 承認対象：<具体的な内容と範囲>
- 承認していない内容：<除外・保留>
承認済み仕様：<欠落のない実装仕様全文>
許可編集ファイル：<具体的パスを列挙。ワークスペース全体等にはしない>
共有ファイル所有者：<具体的担当。担当外の検索/辞書/CSSは変更不可>
成果物：指定ページ・機能の実装と検証結果。資料更新はメイン担当。
検証：構文、リンク、検索、アーカイブ・保存互換、必要な画面幅。
停止条件：未確定設定、許可外の変更、競合、承認版と異なる仕様が必要な場合。
着手状態：受領確認のみ・編集着手待ち。
```

メインは受領確認と所有ファイルを照合し、同じagent IDへ次を送る。

```text
ジョブ<実際のジョブID>の受領確認を確認しました。
<承認済み案IDと版>、許可ファイル<具体的な一覧>の範囲で編集着手を許可します。
この許可は作者承認の代替・追加の設定承認ではありません。
範囲外の変更が必要なら止まって報告してください。
```

依頼に作者承認やファイル範囲が入っていなければ、この着手許可を出さない。編集途中の範囲変更でも改めて記録し、必要な作者承認を取得する。

## E. メインの確認チェック

- [ ] 対象の役割ファイルをメインが末尾まで読んだ。
- [ ] その全文を起動メッセージへ展開した。未展開の欄や要約代替がない。
- [ ] ジョブID、役割版、ハッシュ、案の版、編集許可を記録した。
- [ ] 通常サブエージェントの実IDを取得し、受領確認を読んだ。
- [ ] レビューは設計とは別担当で、対象案が実際に渡された。
- [ ] 実装前に作者がその版・範囲を承認した。
- [ ] 共有ファイルに同時の書き込み担当がいない。
- [ ] 実装担当へ着手許可を渡すまで編集を始めさせていない。
- [ ] 完了報告、根拠、差分、実テストを照合した。
- [ ] arg_playerを開発用サブエージェントとして起動していない。

arg_playerの起動テンプレートは本書には用意しない。別環境での初見テスト計画が承認されるまでは定義の保管のみとする。
